# Data architecture

## Data storage and serving

All data except some geographic data (e.g., parcel GeoJSON and satellite
images) lives in relational form in SQLite on the server. Satellite rasters and
precomputed satellite summaries are generated by `manage.py build_satellite`
from `terreni.geojson` and stored under `SATELLITE_DIR`.

However, to reduce latency, it is always served as compressed pre-computed JSON.
The mapping of relational tables to JSON files is specified in the detailed
domain descriptions.

For tabular data, the format is a JSON object with two fields:

    { "columns": ["row_id", "Data", "Compresa", ...],
      "rows": [[1, "2024-03-15", "Alpe", ...], ...] }

`columns` lists column names once; `rows` is an array of arrays containing pure
data. Every row's first element is `row_id`, used for updates (see below). The
client maps columns by name, so adding a column does not break cached data.

The read-only audit digest is an identity exception: its `row_id` is a stable
`<model-label>:<history-id>` string, rather than a mutable domain row's integer
key. Its timestamp retains UTC microseconds for sorting/export; a separate
hidden label supplies local display time. See [Controllo](page-controllo.md).

### JSON digest regeneration

Digests are regenerated lazily on read, not on write. This avoids wasted work
during batch data entry (where the inserting user's view is already kept current
via cache sync from the POST response).

A small table tracks staleness:

    digest_status(name TEXT PRIMARY KEY, stale BOOLEAN DEFAULT FALSE,
                  dirty_seq INTEGER DEFAULT 0)

Write path: after a successful save, the view marks affected digests as stale:
`UPDATE digest_status SET stale = TRUE, dirty_seq = dirty_seq + 1 WHERE
name IN (...)`. This is the only write-path cost.  `dirty_seq` is a
monotonic token; the read path uses it to detect a write that landed mid
regeneration (see below).

The domain mutation and all its dirty marks must share one database
transaction, even when there is no request nonce. Otherwise interruption after
the mutation can leave an old file permanently marked fresh. Import/clear
services own their invalidation inside their atomic operation; callers must
not defer it until after the service commits. A nonce adds its replay receipt
to this same unit; it is not a prerequisite for mutation/invalidation atomicity.

Dynamic families (`sampled_trees_<survey-id>` and
`mark_trees_<item-id>`) use `mark_stale_prefixes()`. It updates every existing
`DigestStatus` row with the requested prefix. A never-read dynamic digest has
neither a status row nor a file and will be generated from current data on its
first request, so no placeholder status rows are needed.

**The "affected digests" set is whatever the digest's generator reads,
transitively.** A write to table T must invalidate every digest D whose
`generate_D()` reads T — directly or via a join.  Forgetting one is a silent
bug: the on-disk file stays, the staleness flag stays False, and the next
read serves a stale digest *even after a page reload* (the cache miss still
hits the un-regenerated file).

Each page's doc (`docs/page-*.md`) carries the authoritative
write→digest invalidation table for its domain, including cross-domain
cases (e.g., a prelievi harvest write that marks `harvest_plan_items`
stale).

When you add a new write endpoint, audit every `generate_*()` in
`apps/base/digests.py` and add `mark_stale()` for each digest that touches
the written table.  When you change a `generate_*()` to read a new table,
audit every write endpoint that touches that table.  Tests under
`TestDigestInvalidation` (`test/test_campionamenti_views.py`,
`test/test_prelievi_views.py`, `test/test_piano_di_taglio_views.py`,
`test/test_hypso_views.py`) lock the contract: each test performs a write and
re-reads the affected digest via the public endpoint, asserting that
materialized columns reflect the change.  Add equivalent tests for any new
write/digest pair.

Read path (conditional GET for a digest):
1. Check stale flag for the requested digest (one PK lookup).
2. If stale (or the file is absent), regenerate the digest:
   a. Snapshot `dirty_seq` for the digest.
   b. Generate the digest and write it to a temp file (gzip-compressed).
   c. `os.rename()` the temp file to the digest path (POSIX-atomic).
   d. Clear the stale flag *only if no write intervened*: `UPDATE
      digest_status SET stale = FALSE WHERE name = ? AND dirty_seq = ?`,
      passing the value snapshotted in (a).

   The `dirty_seq` compare-and-swap closes a lost-update race.  A boolean
   `stale` flag cannot tell "the TRUE I observed before generating" from "a
   TRUE a concurrent writer set while I was generating": clearing on
   `stale = TRUE` would erase that newer write's mark, leaving an on-disk
   digest that predates the write yet reads as fresh forever — only a manual
   file delete recovers it (the extreme case is an empty digest produced when
   the generator's snapshot fell inside a destructive re-import window).
   Because every mark bumps `dirty_seq`, an intervening write makes the
   snapshotted value stale, the `UPDATE` matches no row, and the digest
   stays flagged so the next read regenerates against the newer data.

   The file is renamed into place (c) *before* the flag is cleared (d), so an
   interrupted generation leaves a complete file and may over-report staleness.
   This assumes serialized generation, as with the current single synchronous
   Gunicorn worker. Cross-process generation ownership (including concurrent
   management commands) is a separate prerequisite for adding workers.

3. Open the published file and compute its quoted SHA-256 ETag over the gzip
   bytes. Compare `If-None-Match` with that ETag: a match returns 304; otherwise
   stream the same open file with 200. Both responses carry ETag and
   Last-Modified. Weak/list/wildcard If-None-Match validators are supported.
   Hashes are cached in a bounded process-local LRU keyed by file identity,
   size and nanosecond modification/change times; replacement or backdating
   cannot reuse a previous file's hash. The ETag identifies the published bytes,
   not the current `dirty_seq`, which may be ahead of the published file.

Digest responses never return 304 on a date alone: whole-second Last-Modified
values cannot distinguish two generations published within the same second.
An older client sending only If-Modified-Since receives 200 until it starts
sending ETags. Other conditional files (GeoJSON, satellite data, photos) retain
their existing date-based validation unless explicitly opting into ETags.

All digest generation logic lives in `apps/base/digests.py`, since digests
often span multiple domain tables.

Digest files are gzip-compressed (stored as `.json.gz`) and served with
`Content-Encoding: gzip`.

Digest responses are served `Cache-Control: no-store`.  The app is its own
cache — the in-memory client store (below) plus the conditional GET above —
so the browser's HTTP cache must stay out of the loop.  Without `no-store` a
`Last-Modified` response with no `Cache-Control` is eligible for the
browser's *heuristic* cache: after a write the in-memory store is patched,
but a reload would serve the browser's stale copy without ever revalidating
(a stale table even though the server and DB are correct).  `no-store` still
lets the conditional GET answer 304 for unchanged digests, so it costs no
bandwidth.

## Caching

Data is cached client-side in memory, keyed by `data_id` (one per
server-side JSON file). Page reloads clear all cache state.

On every domain switch the app renders from cache immediately, then
fires background conditional GETs (If-None-Match for digests) for every visible
dataset, re-rendering on 200. A 5-minute timer repeats this even
without navigation. First load (empty cache) shows a "Caricamento..."
modal until data arrives.

The client retains the ETag with the cached dataset and sends it on manual
loads and background refreshes. Last-Modified remains a fallback for endpoints
that do not supply ETags. A 304 retains the cached body; eviction removes both
the body and its validators so the next fetch is unconditional.

Each dataset also has a local revision independent of its cached body. Exact
invalidation advances that revision even if no body exists. Prefix invalidation
covers every matching registered, cached or previously known ID, including
in-flight first loads and entries already evicted. Patches/deletes advance it
too, even when the digest has not loaded and its column shape is unavailable;
they never synthesize a partial digest from a row patch.

A fetch snapshots the entry and revision before requesting data. An obsolete
200 or 304 cannot populate the cache, restore evicted validators, or notify
listeners. `load()` returns an already newer cached body when available;
otherwise it retries unconditionally against the current generation, so a
discarded initial response does not leave the mounting page without data.
Exact/prefix invalidations notify affected known IDs even when they had no
cached body. Unrelated IDs and requests are unaffected. Revisions live for the
SPA session, like registered URLs; a page reload resets both.

## Data entry and cache updates

Forms are Django-rendered HTML fragments displayed in overlay modals
(see `docs/ui-design-patterns.md` §Modals). The data entry flow:

1. JS fetches form HTML (including CSRF token + idempotency nonce) via
   `fetchModalForm` and renders it in a modal. URL does not change.
1. Client-side JS validation gates the submit button.
1. On submit, JS intercepts the POST (with CSRF token + nonce).
1. Server checks nonce for dedup (prevents double-writes on network
   retry). Used nonces are pruned after 24 hours.
1. Server validates and responds.

### Request contract

Most mutating endpoints receive a JSON POST. Malformed JSON and non-object
JSON bodies receive the standard validation-error response. Form controls are
serialized into a JSON object; CSV import file inputs are read as bytes in the
browser and sent
as base64 strings in their normal file field (`file`, `fustaia_file`, or
`ceduo_file`). The server decodes that field back to bytes before running the
shared CSV reader, so UTF-8 and CSV validation remain server-owned. These
JSON bodies and multipart non-file fields are capped by `DATA_UPLOAD_MAX_MEMORY_SIZE`,
defaulting to the Ipso upload limit of 30 MiB and configurable with
`DJANGO_DATA_UPLOAD_MAX_MEMORY_SIZE`.

JSON decoding is shared and cached on the request, including nonce inspection
and Ipso's protocol adapter. Invalid encoding, non-object desktop payloads,
non-finite JSON numbers (including overflowing exponents) and decoder recursion failures return normal protocol
validation errors. The desktop `parse_json_body()` also applies shared wire-type
guards before views dereference text or numbers: objects/arrays cannot become
text, booleans/floats cannot become integer IDs, and null text means blank.
Unknown fields remain ignored for forward compatibility. Free-text parcel/area
numbers retain their existing string semantics.

Shared numeric helpers enforce signed 64-bit integer storage bounds, safe
coordinate conversion and geographic ranges. Decimal precision comes from the
owning model field rather than a second set of hard-coded digit limits. The
sample normalizers reuse those bounds for manual, CSV and Ipso imports.
`TimestampedModel.save()` checks decimal representability before writing, so
derived volume/mass or aggregate values cannot pass the input checks and then
leave an unreadable SQLite row. It neither changes rounding nor imposes a
scientific diameter/height cutoff. Direct bulk/update operations must preserve
the same checks themselves; they bypass model `save()`.
CSV integer parsing still tolerates integral spreadsheet values such as `12,0`;
the JSON/form integer edge accepts only actual integers or bare integer strings.
Nested shoot/grid-point arrays use the same object/type checks, and boolean
flags use the shared truth parser (`"false"` is false). User role/login-method
choices are validated before saving.

Boundary failures use the existing HTTP 400 envelope: `status`, localized
`message`, `errors`, and optional replacement `html`. They do not send success
patches or consume the nonce. A response without replacement HTML is displayed
inline by the existing form handler; entered values stay in place and submit
controls are restored so the form can be corrected and resubmitted. Domain
validation and row-version conflicts retain their existing behavior.
`InputValidationMiddleware` runs inside the nonce transaction and translates
only the explicit `InputValidationError` raised by these storage/calculation
checks. A rejected write unwinds its transaction before the 400 is returned;
unexpected arithmetic/programming exceptions are not broadly hidden as input
errors. Native Ipso upload parsing keeps its own existing error envelope.

Bosco observation saves use multipart form data so photos can be sent as file
parts. Nonce replay applies to both JSON and multipart POSTs: retrying a
successful observation create or edit returns its original response without
creating another observation/photo or reapplying the edit.

Every retryable write carries a client-generated `nonce`. Versioned row edits
and deletes also carry the cached `version`; a missing version is treated as
stale (`0`) and returns a conflict instead of weakening optimistic locking.

### Retry receipts and write transactions

Authenticated API POSTs with a nonce use the same protocol for JSON and
multipart forms. A nonce is a nonblank string of at most 64 characters, scoped
to its user and retained for 24 hours. Its receipt also stores a SHA-256 request
identity: method, path/query and canonical JSON, or normalized form fields and
file metadata/checksums. JSON key order/whitespace and multipart boundaries do
not affect identity; the hidden CSRF form field is excluded. File streams are
hashed in chunks and rewound before the view reads them.

Views parse expensive inputs first, then call `begin_nonce_write(request)` just
before their first database write or mutating import helper. This opens an
outer transaction and inserts the unique `(nonce, user)` claim as its first
write. Existing view/service atomic blocks become nested savepoints. A
concurrent identical request waits for the claim: it either replays the
completed receipt or, if the first attempt rolls back, performs the operation
itself. A competing request must not read a database snapshot inside an atomic
block before claiming its nonce.

`success_response()` stores the response in that same transaction. Middleware
commits only after response construction succeeds, so domain changes, audit
history, digest dirty marks and the replay receipt commit together. Exceptions
and rejected responses roll back the domain transaction and claim; their nonce
can be retried. Ipso validation diagnostics are saved separately after rollback,
without changing forestry data or consuming the nonce. Requests without a
nonce retain their existing transaction boundaries and have no replay guarantee.

When adding an endpoint, call `begin_nonce_write()` before any mutation and
finish successful nonce-backed writes with `success_response()`. The request's
SQL write guard fails before an unclaimed ORM mutation, catching forgotten
boundaries. Avoid parsing photos/CSV or making network calls while holding the
write lock. Schedule file deletion with `transaction.on_commit()`; unavoidable
file rewrites must register rollback restoration. Database transactions do not
make filesystem operations atomic across process/host failures.

Reusing a completed nonce for a different operation or payload returns HTTP
409, not the earlier operation's response. Pre-upgrade receipts without a
request hash remain replayable until their normal expiry, avoiding duplicates
immediately after deployment. Public Ipso uploads use their separate session
UUID/checksum protocol, not these authenticated web-form receipts.

Media-changing observation/Ipso requests additionally hold the shared runtime
snapshot lock through nonce commit/rollback and filesystem hooks.
`RuntimeSnapshotMiddleware` wraps `NonceMiddleware` so a live backup's exclusive
snapshot-copy phase cannot interleave with those operations. Compression and
verification use private copies after the exclusive lock is released. See
[Backups](backups.md) and [Osservazioni](page-osservazioni.md#photo-backup-and-recovery).

### Response contract

Payload is always JSON.

**Success** (200): `{ data_id, row_id, patches: [{ data_id, row_id, record }],
deletes: [{ data_id, row_id }], invalidates: { data_ids: [...], prefixes: [...] } }`.
The top-level `data_id`/`row_id` identify the primary entity; row payloads
travel only through `patches` and `deletes`. The client applies every patch
and re-renders touched views. `invalidates` is optional and evicts full cached
digests by exact ID or dynamic-family prefix; it is used when a write changes a
whole aggregate, schema/column set, global interpretation, or too many rows for
a safe optimistic patch. Eviction also invalidates an in-flight fetch snapshot,
and the next `cache.load()` is unconditional. Other digests update on the next
background conditional GET unless the response carries their rows or explicitly
invalidates them.

**Validation error** (400): `{ status: "validation_error", message, html }`.
Modal re-displays the form with the error. Rare — client-side
validation catches most problems first.

**Conflict** (400): `{ status: "conflict", message, data_id, row_id, record, html }`.
Another user modified the row between cache refresh and submit. Modal
shows the server's current state; user can re-submit or dismiss (which
updates the cache with the returned record).

**Nonce reuse conflict** (409): `{ status: "conflict", message }`. The nonce
already belongs to a different successful request; reopen the form to obtain
a fresh nonce. This is distinct from the row-version conflict above.

## Data deletion and cache updates

If the user deletes a record (more on the UI details of this below), the UI
displays an alert warning that the action cannot be undone. 

If the user confirms, a POST is sent to the server as for data insertion / edit
above.

1. Successful responses contain the deleted row in `deletes`. The client removes
   the given id from the cache.

1. Domain validation can still refuse protected deletes, such as an area
   referenced by samples or a harvest plan with active items.

1. Deletes with a preflight version read recheck the version at the write
   boundary using `check_delete_version()` inside `transaction.atomic()`.
   Its conditional no-op UPDATE acquires SQLite's write lock before deletion
   without altering the version, modified time or audit history. An intervening
   edit returns the current conflict row; an intervening deletion returns 404.
   The lock lasts through the deletion and all affected digest dirty marks.

1. Conflict means that a row was edited since last cache refresh. The response
   contains no HTML but a valid record. The cache is updated as for a successful
   update. The error message is displayed in a modal and the user has the chance
   to try deletion again.

## Optimistic table updates — the contract that keeps writes snappy

Every write that mutates a row in a user-visible table MUST return the
full row as a `patches` entry shaped identically to the corresponding
JSON digest: `{data_id, row_id, record}`. Bulk writes return one patch
per row. The client applies the generic envelope with
`cache.applyResponseChanges`, then re-renders touched views from cached
data. No network round trip is needed on the hot path, and no
server-side digest regeneration is needed on the hot path. The
server-side `mark_stale()` flag still runs so the next cold reader (or
the next background refresh) regenerates the on-disk digest.

When a write also bumps a *materialised* value in another digest
(e.g., a tree-save changes `samples.N_alberi`), the response carries
those side-effect rows as additional patches. The client patches every
affected cache and re-renders the touched views.

When the affected value is a full-table aggregate or changes membership or
column shape, return `invalidates` instead. Server staleness and client
invalidation are complementary: `mark_stale()` / `mark_stale_prefixes()` make
the next read regenerate the file, while the response prevents the current SPA
session from rendering an old in-memory copy first. An ID must not be both
invalidated and patched in the same response because invalidations are applied
first and remove the patch target.

**The contract that prevents drift.**  Extract a `build_<digest>_record`
helper in `apps/base/digests.py` and call it from BOTH the digest
generator and every write view.  Lock the column-shape contract with
a test that builds a fresh row through the digest generator and a
record through the write view, then asserts they are equal.  See
`build_harvest_record` for the original pattern.

Bulk paths (CSV imports) that would return megabytes of records may
skip the optimistic path — `tree_csv_import_view` is the documented
exception.
